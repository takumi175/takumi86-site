ミニPCを買って自宅サーバーを立てた。二日かけて、仮想化基盤・DNSサーバー・監視ダッシュボード・自作アプリのホスティングまで一通り動くところまで持っていった。

その過程で、ハードウェアの罠を一つ踏んだ。同じ本体に付いている2つのLANポートで、実効速度が56倍違ったという話だ。結論から書くと、原因の切り分けに一番時間を使った。

## 買ったもの

GMKtec M8。AMD Ryzen 5 PRO 6650H、メモリ16GB、SSD 512GB。中古のノートPCを流用する手もあったが、24時間動かすなら消費電力と静音性を優先したかった。

一つ誤算があった。**メモリが LPDDR5 の基板直付けで、増設できない。** 購入前に「DDR5 16GB」としか書かれていなかったので、後から足せるものだと思い込んでいた。BIOS の画面で `LPDDR5` の表記を見て気づいた。

これは後の設計に効いてくる。ファイルシステムに ZFS を選ばなかったのは、ARC がメモリを大きく使うからだ。16GB 固定なら ext4 の方が安全だった。

## Proxmox を入れる

ハイパーバイザには Proxmox VE を選んだ。Debian ベースで、VM と LXC コンテナの両方を同じ管理画面から扱える。

インストール自体は素直だったが、いくつか引っかかった点がある。

**USBメモリの書き込みは DD モードで。** Rufus 4.15 は Proxmox の ISO を検出して自動的に DD モードを適用してくれた。以前のバージョンだと ISO/DD の選択ダイアログが出て、ここで ISO を選ぶと起動しない。

**BIOS で確認すべき項目は3つ。** SVM Mode（AMD の仮想化機能）、IOMMU、そして Auto Power On。最後のものは「停電から復帰したとき自動で電源が入る」設定で、無人運転するサーバーには必須だ。既定では `Power off` になっていた。

**エンタープライズリポジトリの無効化。** これをやらないと `apt update` が 401 で止まる。管理画面から No-Subscription リポジトリを追加すれば解決する。

Proxmox 9 系は Debian 13 ベースになり、APT の設定ファイルが deb822 形式に変わった。手で書くなら `bookworm` ではなく `trixie` を指定する必要がある。GUI から追加すれば意識しなくていい。

## LANポートの罠

ここからが本題だ。

コンテナのテンプレートをダウンロードしていたら、異様に遅い。**124MB のファイルに48分かかった。** 平均 43.6KB/s。家の回線は決して速くないが、それでもノートPCでは 17Mbps 出ていた。桁が違う。

切り分けを始めた。

```
$ ethtool nic1 | grep -i Speed
        Speed: 1000Mb/s
```

リンク速度は正常。ケーブルも CAT6a で問題なし。

```
$ ethtool --show-eee nic1
EEE status: enabled - active
```

省電力機能（EEE）が有効だった。Realtek の NIC ではこれが原因で速度が落ちる報告がある。切ってみたが、42.5KB/s のまま。効果なし。

次に、同じケーブルをノートPCに挿し替えて測った。17Mbps 出た。**中継機は正常で、M8 側に問題があると確定した。**

ここで、M8 にはもう一つ LAN ポートがあることを思い出した。使っていない方を有効にして測ってみる。

```
$ ip link set nic0 up
$ dhclient nic0
$ wget -O /dev/null http://.../debian-13-standard_13.6-1_amd64.tar.zst
   11.54M  2.36MB/s
```

**2.36MB/s。56倍。**

MAC アドレスは連番（`...ce91` と `...ce92`）で、おそらく同じチップの2ポート構成だ。それなのに片方だけが遅い。ドライバの問題なら両方遅いはずなので、ポート固有の不良と考えるのが自然だろう。

Proxmox のブリッジ `vmbr0` が束ねるポートを `nic1` から `nic0` に変更して解決した。管理画面から `編集` → ブリッジポートを書き換えて `設定を適用`、あとはケーブルを挿し替えるだけだった。

返品も考えたが、2つあるうちの良い方を使えば実用上の問題はない。同じ症状で悩んでいる人がいたら、**もう一方のポートを試してみる価値はある。**

### 副次的な発見

この切り分けの途中で、ルーティングテーブルの読み方を実地で学ぶことになった。

`nic0` に IP を割り当てても外に出られない。`ip route` を見ると、

```
default via 192.168.11.1 dev vmbr0 proto kernel onlink linkdown
```

デフォルトルートが `vmbr0` を向いていて、しかも `linkdown`。ケーブルが刺さっていない方に全パケットを流していた。`nic0` 経由のルートを追加して、古い方を削除したら通った。

教科書で読むと当たり前の話だが、実際に詰まって初めて腹に落ちる。

## 何を載せたか

ネットワークが直ってからは早かった。

### Pi-hole

DNS レベルで広告をブロックする。LXC コンテナに 512MB 割り当てれば十分動く。

面白いのは仕組みそのものだ。広告配信ドメインへの問い合わせに `0.0.0.0` を返すだけ。「嘘をつく DNS サーバー」と考えると分かりやすい。

ブラウザ拡張と違って**家中の全端末に効く。** スマートテレビやスマホアプリの広告にも作用する。

ログを眺めると、Chrome が数秒おきに `beacons.gvt2.com`、`beacons2.gvt2.com`、`beacons3...` と順番に叩いているのが見える。ブロックされたので代替ホストを次々試しているわけだ。応答時間は 7〜14 マイクロ秒。リストを引くだけなので、外部に問い合わせる場合と比べて桁違いに速い。

### 監視基盤

InfluxDB と Grafana を Docker で立て、各機に Telegraf を入れた。CPU・メモリ・ディスク・温度を30秒おきに収集している。

M8 からは温度センサーが11個も取れた。CPU、内蔵GPU、SSD 3系統、Wi-Fi チップ、そして**あの Realtek NIC の温度まで**見える。速度問題で散々やり合った相手が、グラフの中で淡々と 36℃ を保っている。

ラズパイの CPU 温度は 48℃ 前後、M8 は 36℃ 前後。小さい筐体でファンレスに近い構成だと、こういう差が出る。

Grafana でグラフが点線になって繋がらない現象に少し悩んだ。原因は集計間隔で、`Query options` の `Min interval` を収集間隔と同じ 30秒 に合わせれば線になる。表示期間を短くすると露呈するタイプの設定ミスだった。

### 自作アプリのホスティング

以前 Render にデプロイしていた中国語単語アプリを、自宅サーバーに引っ越した。React + Flask + PostgreSQL の3層構成。

Docker Compose で3コンテナにまとめ、Nginx をリバースプロキシに置いた。`/` は React のビルド済みファイル、`/api` は Flask へ転送する。この構成にすると**フロントと API が同一オリジンになるので CORS の設定が要らない。**

一つハマったのが PostgreSQL の初期化順序だ。`docker-entrypoint-initdb.d` はファイルをアルファベット順に実行する。元のリポジトリには `scores.sql`、`users.sql`、`words.sql` という名前で置いてあったので、`scores` が `users` より先に走って外部キー参照でエラーになる。`01_users.sql` のように番号を振って解決した。

Render の無料プランはアクセスがないとスリープして、次のアクセスで30秒待たされる。自宅サーバーならその待ちがない。DB の容量制限もない。代わりに自宅の回線と電源に依存するが、個人利用なら悪くないトレードオフだ。

### 外部アクセス

Tailscale を使った。ルーターのポートを一切開けずに、外出先から家のサーバーに繋がる。

M8 を**サブネットルーター**に設定したのがポイントで、これで `192.168.11.0/24` 全体が Tailscale 経由で見えるようになる。機器を追加するたびに設定する必要がない。

ここでも一つ詰まった。設定してもスマホから繋がらない。M8 自身の Tailscale IP には届くのに、その先の LAN に出られない。

```
$ sysctl net.ipv4.ip_forward
net.ipv4.ip_forward = 0
```

IP 転送が無効だった。Proxmox は VM のネットワークをブリッジで処理するので、ルーティングを必要としない。だから既定でオフになっている。有効化したら即座に通った。

一時的な公開には Cloudflare Tunnel を使っている。コマンド一つで `https://～.trycloudflare.com` が発行され、ポート開放なしで外部に見せられる。URL は毎回変わるので、常用するなら独自ドメインが要る。

### 死活監視

Uptime Kuma を別コンテナに立てた。**監視ツールを監視対象と同居させない**のが原則で、開発環境の VM に置くと、実験で壊したときに監視も一緒に止まる。

Discord の Webhook で通知するようにした。何か落ちれば1分以内にスマホに届く。

## 完成した構成

```
M8 (Proxmox VE 9.2.2)  192.168.11.100
 ├ CT100 pihole    .101   DNS広告ブロック
 ├ CT102 metrics   .102   InfluxDB + Grafana
 ├ CT103 monitor   .103   Uptime Kuma
 └ VM101 ubuntu    .15    開発環境 + 中国語アプリ

Raspberry Pi 5     .14    Obsidian同期 (CouchDB)

外出先 ── Tailscale ── 全体
毎週日曜3時 ── 自動バックアップ 3世代
```

ラズパイは以前から Obsidian の同期サーバーとして動いていた。今回 Telegraf を入れて、監視ダッシュボードに統合した。

## やってみて思ったこと

**スナップショットが効く。** Proxmox の最大の利点はこれだと思う。何か試す前に取っておけば、壊しても数秒で戻せる。「壊れたらどうしよう」を考えなくていいので、実験のハードルが劇的に下がる。

**用途ごとに分離する意味。** Pi-hole は常時安定していてほしい。開発環境は壊す前提で使いたい。この2つを1台に同居させると、実験のたびに家のネットが止まる。仮想化はこの問題を解決するためにある。

**トラブルシューティングが一番身についた。** `ethtool` でリンク速度を見て、EEE を疑って外し、ポートを替えて実測し、`ip route` で経路を追い、最後に `ip_forward` に行き着く。この流れは教科書に載っている手順そのものだが、実際に詰まって初めて意味が分かった。

うまくいかない理由を一つずつ潰していく作業が、結局のところ一番の学びだった。

## 残っている課題

**バックアップ先が同じ SSD。** 週次バックアップは設定したが、保存先が本体と同じディスクなので、ハードウェア障害には無力だ。空いている M.2 スロットに1枚足すのが次の課題。

**センサーが未着手。** 温湿度センサーやカメラを買ってあるのだが、ピンヘッダが未実装で**ハンダごてが必要**だと気づいた。InfluxDB と Grafana という受け皿はできているので、ハンダごてさえ手に入れば繋がる。

**CI/CD。** いまはコードを直すたびに SSH で入って `docker compose up -d --build` を叩いている。GitHub に push したら自動でデプロイされる仕組みを作りたい。
